    1. An agent can only write a proposed instance (datasetId ...:kaiku:proposed) with its reason. Nothing physical or published happens without the owner's yes.
      2. 
      
    2. The owner's yes is the only call that writes the default instance, with a named approver. On the public endpoint approve and reject are hidden from the agent.
      3. 
      
    3. The broker notification then applies it: the change is pushed to the business listing. The broker holds both instances, so it is the audit log.

    THE MODEL
    
    
      
      
    • Type Store from Smart Data Models dataModel.PointOfInterest, with name, address, location, category and openingHoursSpecification (schema.org day URIs).
      • 
      
    • @context in the Link header: {{ sdm_context }} and {{ core_context }}.
      • 
      
    • holidayHours is a multi-instance Property: one instance per source, each with datasetId {{ dataset_prefix }}{lastyear|website|google|peers|proposed} and observedAt. The instance without datasetId is the default. holidayHours is ours, not in the SDM context (Orion expands it to its default vocabulary).
      • 
    
    
    
    WHAT DID NOT WORK, SAID PLAINLY
    
    
      
      
    • Orion-LD (post-v1.12.0 build) accepts datasetId instances only when an entity is created. POST and PATCH on /attrs, upsert and batch answer 501. So we read, merge, delete and re-create the entity. Not atomic across processes.
      • 
      
    • The q filter on a key inside an object value is accepted but not evaluated. We subscribe on watched attributes and filter in our handler.
      • 
      
    • A newly added attribute does not fire a subscription, so the status attribute is seeded at creation.
      • 
      
    • The Yext write never depends on the broker: if it is down the chain continues on an in-memory fallback and says "broker offline".
      •
