### Approval render: the "rendered 246" hang (7 Nov)
Not a bad asset or composition bug: all seven clips (remotion/public/appr A B C D F G P) are valid h264 yuv420p 30 fps with the planned frame counts, and stills at 240/244/246/248/252 and a 200-330 range render fine (frame 246 = 8.2 s, inside beat A). The cause is CPU starvation: the VPS has 2 cores with 65-78% hypervisor steal and other Chromium/ffmpeg jobs (aura render, nightly pass) running, so an OffthreadVideo frame fetch (`/proxy?src=.../appr/B.mp4`) outlived Remotion's 28 s delayRender timeout. The first run's workers then sat idle while the progress callback kept printing the last count every 20 s, which looks like a hang at one frame (the second run died with the explicit "delayRender ... not cleared after 28000ms" error at frame ~640).
Fixes: render_approval.mjs now passes timeoutInMilliseconds: 300000; scripts/approval_render_chunks.sh renders 20 frame-range chunks (196 frames), retries each up to 6 times and concats with ffmpeg -c copy, so one timeout costs a chunk, not the film. Other traps: the browser is chromium_headless_shell-1223/chrome-headless-shell-linux64/chrome-headless-shell (chromium-1223/chrome-linux/chrome does not exist), CONC max is 2, start long renders with `setsid nohup ... &`, never `pkill -f`/`pgrep -f` from the same shell line (it matches and kills the tool shell), and /root/hack/bin/heavy queues behind other renders (an aura render held the lock for ~50 min).
